사이드 프로젝트를 만들거나 데이터 분석을 하다 보면 늘 같은 벽에 부딪힌다. "쓸 만한 데이터를 어디서 구하지?" 이때 가장 먼저 떠올려야 할 답이 **정부 공개 API**다. 정부와 공공기관이 운영하는 **공공데이터** API는 무료이고, 출처가 명확해 신뢰도가 높으며, 상업적 활용까지 폭넓게 허용된다. 날씨, 주가 공시, 금리, 버스 도착 시간, 법령 조문까지 — 민간 유료 서비스가 비싸게 파는 데이터의 상당수가 사실은 정부 공개 API로 공짜로 풀려 있다. 이 글의 핵심 메시지는 단순하다. **"데이터를 사기 전에 공공데이터포털부터 검색하라."**

그 출발점이자 허브가 바로 **공공데이터포털(data.go.kr)**이다. 여기 한 곳에서 수만 개 기관의 API를 검색하고, 활용신청을 넣고, 하나의 계정으로 인증키를 관리할 수 있다. 기관별로 흩어진 사이트를 일일이 뒤지기 전에, 대부분의 API가 이 포털에 모여 있다는 점만 알아도 작업 시간이 절반으로 준다.

## 공공 API가 민간 API와 결정적으로 다른 세 가지

표를 보고 곧장 코드부터 짜기 전에, 이 API들이 스트라이프나 트윌리오 같은 상용 API와 성격이 다르다는 점을 알고 시작하는 편이 낫다. 무료라는 것 말고도 다른 점이 세 가지 있고, 셋 다 설계에 영향을 준다.

**첫째, 가용성 약속이 없다.** 상용 API는 "월 99.9% 가동"을 계약으로 보장하고 못 지키면 요금을 깎아 준다. 공공 API에는 그런 약속이 없다. 새벽 정기점검으로 몇 시간 응답이 끊겨도 그건 장애가 아니라 예정된 일이다. 그러니 공공 API를 서비스의 실시간 핵심 경로에 그대로 물리면 안 된다. **받아온 데이터를 자기 저장소에 한 번 눌러 담고, 화면은 그 저장소를 보게 만드는 것**이 사실상의 필수 설계다. 원본이 잠깐 죽어도 화면은 마지막으로 성공한 값을 보여 준다.

**둘째, 변경 공지가 약하다.** 상용 API는 버전을 나누고 폐기 일정을 몇 달 전에 메일로 알린다. 공공 API는 엔드포인트 이름에 붙은 `_2.0` 같은 숫자가 어느 날 조용히 올라가고, 기존 주소는 한동안 살아 있다가 사라진다. 필드명이 바뀌는 경우도 있다. 그래서 응답을 파싱할 때 **없는 필드를 만나면 죽는 코드가 아니라, 없으면 기본값을 쓰고 로그를 남기는 코드**로 짜야 오래 간다.

**셋째, 물어볼 곳이 게시판이다.** 막혔을 때 스택오버플로에 답이 있을 확률이 상용 API보다 훨씬 낮다. 대신 포털의 '문의' 게시판과 각 기관 담당자 연락처가 있고, 실제로 답이 온다. 다만 하루 이틀 걸린다. 일정을 잡을 때 이 왕복 시간을 미리 넣어 두는 편이 좋다.

이 세 가지를 뒤집어 말하면 이렇다. **공공 API는 "실시간 연동 대상"이 아니라 "정기적으로 긁어와 쌓아 두는 원천"으로 다룰 때 가장 안정적이다.** 하루 한 번 도는 배치가 매 요청마다 호출하는 구조보다 거의 항상 낫다.

## 시작하기: 활용신청부터 첫 호출까지

가장 흔한 진입 경로인 **공공데이터포털 기준** 절차는 다음과 같다.

1. **회원가입 & 로그인** — data.go.kr에 가입한다(공동/간편 인증 지원).
2. **API 검색** — 예: "기상청 단기예보", "TAGO 버스도착". 결과에서 *오픈API* 항목을 고른다.
3. **활용신청** — "활용신청" 버튼 → 활용목적 입력 → 제출. 일반 API는 대체로 자동 승인(보통 수십 분~1~2시간)이고, 일부는 담당자 검토로 며칠 걸릴 수 있다.
4. **인증키 확인** — 마이페이지 → 데이터활용 → 개발계정에서 `serviceKey`를 확인한다.
5. **호출** — 발급된 키를 쿼리 파라미터에 넣어 GET 요청을 보낸다.

호출 예시(기상청 동네예보 형태의 의사 URL):

```text
GET https://apis.data.go.kr/1360000/VilageFcstInfoService_2.0/getVilageFcst
  ?serviceKey=발급받은인증키
  &dataType=JSON
  &numOfRows=10
  &pageNo=1
  &base_date=20260627
  &base_time=0500
  &nx=60
  &ny=127
```

```python
# Python 의사코드
import requests

params = {
    "serviceKey": "발급받은_디코딩_인증키",  # requests가 자동 인코딩
    "dataType": "JSON",
    "numOfRows": 10, "pageNo": 1,
    "base_date": "20260627", "base_time": "0500",
    "nx": 60, "ny": 127,
}
r = requests.get(URL, params=params)
print(r.json())
```

### 첫 호출에서 막히는 지점은 대개 네 곳이다

처음 붙일 때 시간을 잡아먹는 지점은 거의 정해져 있다. 네 가지만 알고 가면 반나절이 30분으로 준다.

**1. 인증키 이중 인코딩.** 포털은 인증키를 *Encoding*과 *Decoding* 두 가지로 보여준다. 키에 `+` `/` `=` 같은 문자가 섞여 있을 때, 라이브러리가 이미 URL 인코딩을 한 번 해주는데 거기에 인코딩된 키를 또 넣으면 이중 인코딩이 되어 `SERVICE_KEY_IS_NOT_REGISTERED_ERROR`가 난다. requests의 `params=`처럼 자동 인코딩되는 경로에는 **Decoding 키**를, URL에 직접 문자열로 박을 때는 **Encoding 키**를 쓴다고 기억하면 대부분 해결된다. 이 하나가 초보자 질문의 절반쯤을 차지한다.

**2. 에러도 HTTP 200으로 온다.** 이게 두 번째 함정이자, 운영에 들어가서야 터지는 종류다. 공공 API 상당수는 인증 실패든 한도 초과든 **HTTP 상태코드는 200을 주고 본문 안에 결과 코드를 담아 보낸다.** `response.raise_for_status()`만 믿고 짠 코드는 에러를 정상으로 착각하고 빈 데이터를 그대로 저장한다. 반드시 본문의 결과 코드(`resultCode`·`returnReasonCode` 등 명세마다 이름이 다르다)를 확인하는 분기를 넣어야 한다.

**3. `dataType=JSON`을 무시하는 API가 있다.** JSON을 요청했는데 XML이 오는 경우가 있고, 더 흔하게는 **에러일 때만 XML로 떨어진다.** 정상 응답만 보고 JSON 파서를 걸어 두면 에러 상황에서 파싱 예외가 나며 원인을 못 찾는다. 응답을 파싱하기 전에 `Content-Type`이나 첫 글자가 `<`인지 한 번 보는 방어 코드를 넣어 두는 게 낫다.

**4. 페이징 기본값이 작다.** `numOfRows` 기본값이 10인 API가 많아서, 데이터가 다 안 왔는데 "이 API는 데이터가 없네"로 결론 내리기 쉽다. `totalCount`를 먼저 읽고 페이지를 돌리는 습관을 들이자.

포털에는 이 밖에도 한도 초과·기간 만료·미등록 IP 등에 대한 표준 결과 코드가 정의돼 있다. 처음 붙일 때 **에러 코드 표를 한 번 훑어보고 그대로 분기 로직에 옮겨 두면**, 나중에 원인 모를 빈 응답을 붙들고 헤매는 시간이 사라진다.

## 무엇을 만들 수 있나: 활용 아이디어

조합하기 나름이지만, 곧장 만들어볼 만한 것들이 있다. 출퇴근 시간에 우리 동네 버스 도착(TAGO)과 미세먼지(에어코리아)를 한 화면에 띄우는 위젯, OpenDART 재무 데이터로 관심 종목의 매출·영업이익 추이를 자동 정리하는 대시보드, ECOS 기준금리와 환율을 끌어와 알림을 보내는 봇, 법제처 API로 특정 법령 개정 이력을 추적하는 도구 같은 것들이다. 정부 API의 진짜 가치는 "남들이 일일이 복붙하던 작업을 자동화"하는 데 있다. 앞서 말한 부동산 앱 예시처럼, 핵심은 단일 API의 화려함이 아니라 **여러 출처를 엮어 만드는 조합의 힘**이다.

## 현실적인 주의점과 운영 팁

다만 실무에서 반드시 염두에 둘 제약이 있다.

| 주의 항목 | 내용 |
| --- | --- |
| 트래픽 한도 | 개발계정은 보통 일 1,000~10,000회 등 호출 제한이 있다. 운영 서비스는 별도 *운영계정* 전환·증설 신청이 필요하다. |
| 승인 대기 | 자동 승인이 다수지만 일부 API·민감 데이터는 검토에 며칠 걸린다. 일정에 버퍼를 둘 것. |
| 데이터 갱신주기 | "실시간"이라 해도 갱신 간격이 다르다(예: 동네예보 시간대별 발표). 캐싱·폴링 주기를 갱신주기에 맞춰라. |
| 응답 포맷·스펙 변경 | XML/JSON, 필드명, 엔드포인트가 개편될 수 있다. 코드에 방어 로직과 명세 버전 확인을 둘 것. |
| 이용약관·출처표기 | 상업적 활용 범위와 출처 표기 의무는 API마다 다르다. 배포 전 약관 확인 필수. |

### 어떤 순서로 붙일까 — 난이도 지도

처음이라면 붙이는 순서가 중요하다. 난이도가 꽤 다르기 때문이다.

**쉬운 축**은 한국은행 ECOS와 OpenDART다. 둘 다 자체 포털에서 키를 바로 주고, 문서에 예제가 있으며, 응답 구조가 단순하다. 무엇보다 데이터가 시계열이라 한 번 받아서 눈으로 확인하기 쉽다. 첫 프로젝트로 "기준금리 추이 그래프"나 "관심 종목 매출 추이"를 만들어 보면 감이 온다.

**중간**은 기상청과 교통 계열이다. 데이터 자체는 풍부한데 좌표 체계나 노선 ID 같은 **자기만의 식별자 체계**가 있어서, 그 매핑을 이해하는 데 시간이 든다. 기상청은 위경도가 아니라 격자 좌표를 쓰고, 버스 API는 도시코드와 노선 ID를 먼저 조회해야 도착 정보를 부를 수 있다. 이 단계에서 "API 하나가 아니라 두세 개를 순서대로 불러야 한 화면이 나온다"는 걸 배우게 된다.

**어려운 축**은 법령과 공간정보다. 법제처 API는 응답이 법조문 구조 그대로라 XML이 깊고, V-World는 지도 렌더링까지 얹어야 결과가 보인다. 여기까지 오면 API 호출보다 데이터 구조를 이해하는 데 시간이 더 든다.

정리하면 **ECOS·OpenDART로 감을 잡고 → 기상청·교통으로 식별자 체계를 익히고 → 필요할 때 법령·공간정보로 넘어가는** 순서가 가장 덜 지친다. 첫 API로 법제처를 고르면 대부분 도중에 포기한다.

개인적으로 정부 공개 API를 여러 번 써본 입장에서, 가장 큰 장점은 "공짜"보다 "출처의 권위"다. 기상청·한국은행·금감원이 직접 제공하는 숫자라는 사실 자체가 서비스의 신뢰를 만든다. 반대로 가장 큰 단점은 문서 품질의 편차다. 잘 정리된 API가 있는가 하면, 예시 하나 없이 XML 스키마만 던져주는 곳도 있다. 그래서 실전 팁은 이렇다 — **새 API를 붙이기 전에 포털의 "활용사례"와 깃허브에 공개된 래퍼/예제부터 검색하라.** 누군가 이미 함정을 다 밟아두었을 확률이 높다.

정리하면, 데이터가 필요할 때의 첫 행동은 결제가 아니라 검색이다. data.go.kr에서 키워드 한 번 쳐보는 것. 거기서 시작하면 대부분의 데이터 문제는 무료로, 그리고 신뢰할 수 있는 출처로 풀린다.
