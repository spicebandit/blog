**답부터. 벡터DB도 임베딩도 필요 없다. 마크다운 폴더 세 개와 규칙 파일 하나면 된다.**

"내 자료를 AI가 읽게 하고 싶다"고 하면 보통 RAG를 떠올린다. 벡터 데이터베이스를 세우고 임베딩 파이프라인을 붙이는 그 방식이다. **자료가 수백 개 수준이라면 그럴 필요가 없다.**

안드레이 카파시가 2026년 4월 공개한 **LLM Wiki** 패턴이 그 답이다. 제품이 아니라 폴더 구조와 규칙의 조합이고, 클로드 코드 같은 에이전트만 있으면 오늘 만들 수 있다.

| 질문 | 한 줄 답 |
|---|---|
| 뭐가 필요한가 | **폴더 3개 + CLAUDE.md 하나.** 벡터DB·임베딩 없음 |
| RAG와 뭐가 다른가 | RAG는 매번 새로 찾고, **이건 쌓인다** |
| 언제 이걸 쓰나 | 소스가 **100개 안팎**일 때 |
| 설치는 | `npx add-skill Astro-Han/karpathy-llm-wiki` |

## 왜 RAG가 아니라 위키인가

답부터: **RAG는 지식이 안 쌓이기 때문이다.**

카파시가 지적한 지점이 이거다. 보통 RAG는 질문이 들어올 때마다 원문 조각을 검색해 답을 만든다. 잘 작동한다. 그런데 **어제 답한 내용이 오늘 남아 있지 않다.** 같은 자료를 백 번 물어보면 백 번 처음부터 읽는다.

그가 쓴 문장이 핵심을 찌른다.

> "지식베이스 유지에서 지루한 부분은 읽기나 생각이 아니라 **기록 관리(bookkeeping)**다."
>
> "**LLM은 지루해하지 않고, 교차 참조 갱신을 잊지 않으며, 한 번에 파일 15개를 손볼 수 있다.**"

사람이 위키를 관리할 때 무너지는 지점은 새 글을 쓰는 게 아니다. **새 글을 쓴 뒤 관련된 기존 문서 열 군데를 고치는 일**이다. 그게 귀찮아서 다들 안 한다. LLM은 그걸 안 귀찮아한다.

그래서 LLM Wiki는 **자료를 넣는 시점에** 정리를 끝낸다. 질문이 오면 이미 정리된 위키를 읽는다. **쓸수록 좋아진다.**

### 비유 둘 — 카파시의 것과 해설자의 것

카파시 본인은 이렇게 비유했다. **"옵시디언이 IDE, LLM이 프로그래머, 위키가 코드베이스다."** 사람이 도구를 고르고, LLM이 그 안에서 일하고, 결과물이 쌓인다는 그림이다.

이 패턴을 풀어 쓴 Starmorph 가이드는 한 걸음 더 나간 비유를 든다. 구조를 이해하기엔 이쪽이 빠르다.

| 위키 | 컴파일러로 치면 |
|---|---|
| `raw/` (원본) | 소스코드 |
| LLM | 컴파일러 |
| `wiki/` (정리본) | 실행 파일 |
| lint (점검) | 테스트 |
| 질문 | 런타임 |

소스코드를 고치면 다시 빌드한다. 자료를 넣으면 위키를 다시 정리한다. 같은 이야기다.

## 구조 — 세 층이 전부다

답부터: **원본, 정리본, 규칙. 이 셋이다.**

아래 트리는 널리 쓰이는 관례다. **카파시 원문은 하위 폴더 이름까지 정해 두지 않았고**(페이지 유형만 언급한다), 뒤에 소개하는 설치용 스킬은 주제별 폴더(`raw/<주제>/`, `wiki/<주제>/`)를 쓴다. **스킬을 쓸 생각이면 이 트리를 미리 만들지 말고 스킬 방식을 따르는 편이 낫다.**

```
mywiki/
├── raw/              ← ① 원본. 절대 수정 안 함
│   ├── articles/
│   ├── papers/
│   └── data/
├── wiki/             ← ② LLM이 쓰고 관리
│   ├── index.md      (목차 — 매 작업마다 갱신)
│   ├── log.md        (작업 기록 — 추가만)
│   ├── concepts/     (개념)
│   ├── entities/     (인물·기업·기관)
│   ├── sources/      (원본 요약)
│   └── comparisons/  (비교)
├── outputs/          ← 날짜별 리포트
└── CLAUDE.md         ← ③ 규칙서
```

**① `raw/` — 절대 건드리지 않는다**

이게 이 패턴에서 가장 중요한 규칙이다. **AI는 여기서 읽기만 하고 절대 쓰지 않는다.** 위키의 모든 주장은 여기 있는 파일로 역추적돼야 한다. 원본이 변하면 무엇이 근거였는지 알 수 없게 된다.

**② `wiki/` — LLM이 주로 쓰고, 사람이 주로 읽는다**

여기가 뒤집혀 있다는 점이 재밌다. 보통 위키는 사람이 쓰고 사람이 읽는데, 여기서는 **LLM이 쓰고 사람이 읽는다.**

특별한 파일 두 개가 있다.
- **`index.md`** — 무엇이 어디 있는지 적힌 목차. 질문이 오면 AI가 **이걸 먼저 읽는다**
- **`log.md`** — 언제 무엇을 했는지의 기록. **추가만 하고 고치지 않는다**

**③ `CLAUDE.md` — 가장 중요한 파일**

AI를 위키 관리자로 만드는 규칙서다. 여기에 무엇을 적느냐가 위키의 품질을 결정한다.

## CLAUDE.md에 뭘 적나

답부터: **페이지 형식, 이름 규칙, 그리고 세 가지 작업 절차다.**

권장되는 구성은 이렇다.

**① 페이지마다 YAML 앞머리를 붙이게 한다**

카파시 원문은 앞머리를 선택 사항으로만 언급한다. 아래는 **해설 가이드들이 정착시킨 템플릿**이고, 실제로 써 보면 있는 쪽이 훨씬 낫다.

```yaml
---
title: 가스터빈 공급 병목
type: concept          # concept | entity | source-summary | comparison
sources:
  - raw/articles/oilprice-2026-09.md
related:
  - "[[데이터센터 전력수요]]"
  - "[[GE 베르노바]]"
confidence: high       # high | medium | low
updated: 2026-09-21
---
```

**`sources`와 `confidence`가 핵심이다.** 모든 페이지가 어느 원본에서 왔는지 적고, 얼마나 확실한지 표시하면 나중에 검증할 수 있다. 이게 없으면 AI가 쓴 글을 믿을 근거가 사라진다.

**② 이름 규칙을 정한다**

파일명은 kebab-case, 문서 간 연결은 `[[위키링크]]`. 옵시디언을 쓴다면 그대로 호환된다.

**③ 세 가지 작업의 절차를 적는다**

이게 다음 항목이다.

### 그대로 복사해 쓸 수 있는 규칙서

처음 시작할 때 쓸 만한 최소 버전이다. 여기서 출발해 본인 일에 맞게 늘리면 된다.

```markdown
# 이 저장소는 LLM Wiki다

## 폴더 규칙
- `raw/` — 원본. **절대 수정·삭제하지 않는다.** 읽기 전용이다.
- `wiki/` — 네가 만들고 관리하는 정리본.
- `outputs/` — 날짜를 단 리포트.

## 모든 위키 페이지가 지켜야 할 것
파일명은 kebab-case. 문서 연결은 [[위키링크]].
페이지 맨 위에 반드시 아래 앞머리를 붙인다.

---
title: 문서 제목
type: concept | entity | source-summary | comparison
sources:            # raw/ 아래 실제 파일 경로. 없으면 페이지를 만들지 마라
  - raw/...
related:            # 관련 문서의 [[위키링크]]
  - "[[...]]"
confidence: high | medium | low
updated: YYYY-MM-DD
---

**근거 없는 문장을 쓰지 마라.** 모든 주장은 sources의 파일로 역추적돼야 한다.
추정이면 confidence를 낮추고 본문에 추정임을 밝힌다.

## 작업 1 — ingest (자료 넣기)
1. raw/의 새 파일을 읽고, 무엇이 중요한지 먼저 나에게 말한다
2. wiki/sources/ 에 요약 페이지를 만든다
3. **관련된 기존 페이지를 전부 찾아 갱신한다** (이 단계를 건너뛰지 마라)
4. 필요하면 새 개념·개체 페이지를 만든다
5. wiki/index.md 를 갱신한다
6. wiki/log.md 맨 아래에 한 줄 추가한다 (날짜 · 넣은 자료 · 바뀐 페이지)

## 작업 2 — query (질문)
1. wiki/index.md 를 먼저 읽어 관련 페이지를 고른다
2. 그 페이지들만 읽고 답한다. raw/ 를 다시 뒤지지 마라
3. 답에 [[위키링크]]로 근거를 단다
4. 위키에 없는 내용이면 **"위키에 없다"고 말한다.** 지어내지 마라

## 작업 3 — lint (점검)
다음을 찾아 outputs/lint-YYYY-MM-DD.md 로 보고한다.
- 페이지 간 모순
- 고아 페이지 (들어오는 링크 없음)
- 링크는 걸렸는데 없는 페이지
- updated 가 6개월 이상 지난 페이지
```

**여기서 중요한 문장 두 개가 있다.** `sources`가 없으면 페이지를 만들지 말라는 것과, 위키에 없으면 **없다고 말하라**는 것이다. 이 둘이 빠지면 AI가 그럴듯한 내용을 채워 넣고, 그 순간 위키를 믿을 수 없게 된다.

## 작업은 세 가지뿐이다

답부터: **넣고(Ingest), 묻고(Query), 점검한다(Lint).**

### Ingest — 자료를 넣을 때

`raw/`에 새 문서를 넣고 AI에게 시키면 이 순서로 돈다.

1. 문서를 읽고 **무엇이 중요한지 먼저 이야기한다**
2. `wiki/sources/`에 요약 페이지를 만든다
3. **관련된 기존 개념·개체 페이지를 연쇄 갱신한다** — 카파시 표현으로 "한 번에 파일 15개"까지 손댄다
4. 필요하면 새 페이지를 만든다
5. `index.md`를 갱신한다
6. `log.md`에 기록을 남긴다

**3번이 이 패턴의 값어치다.** 사람이라면 절대 안 하는 일이다.

### Query — 물어볼 때

1. **`index.md`를 먼저 읽어** 관련 페이지를 찾는다
2. 그 페이지들을 읽고 종합해 답한다
3. `[[위키링크]]`로 어디서 왔는지 인용한다
4. **답이 쓸 만하면 그것도 페이지로 저장한다**

4번 덕분에 지식이 복리로 쌓인다. 오늘 한 질문의 답이 내일의 자료가 된다.

### Lint — 정기 점검

위키가 커지면 반드시 망가진다. 그래서 점검 작업이 따로 있다.

- 페이지끼리 **말이 안 맞는 곳**
- **고아 페이지** — 아무도 링크하지 않는 문서
- **참조는 됐는데 없는 개념** — 링크는 걸렸는데 페이지가 없는 것
- **오래된 주장** — 갱신이 필요한 내용

결과는 `outputs/`에 날짜를 달아 남긴다.

## 실제로 만들기 — 5단계

답부터: **폴더 만들고, 깃 켜고, 규칙 쓰고, 자료 넣고, 돌린다.**

**1단계 — 폴더 만들기**

```bash
mkdir -p ~/mywiki/{raw/{articles,papers,data},wiki/{concepts,entities,sources,comparisons},outputs}
```

**2단계 — 깃 초기화**

```bash
cd ~/mywiki && git init
```

**선택이 아니라 필수다.** AI가 위키를 통째로 고치는 구조라, 되돌릴 수 없으면 사고가 난다. 매 ingest 전후로 커밋하는 습관을 들이는 게 좋다.

**3단계 — CLAUDE.md 쓰기**

앞에서 본 내용을 적는다. **처음부터 완벽할 필요 없다.** 쓰다 보면 AI가 헷갈려 하는 지점이 나오는데, 그때마다 규칙을 추가하면 된다.

**4단계 — 첫 자료 넣기**

`raw/`에 문서를 몇 개 넣는다. 기사 스크랩, PDF, 회의록, 예전에 쓴 글 무엇이든 된다.

**5단계 — 첫 ingest 돌리기**

해당 폴더에서 클로드 코드를 실행하고 자료를 넣으라고 시킨다.

**완료 신호**: `wiki/` 아래에 페이지가 생기고 `index.md`에 목록이 잡히면 된다.

### 직접 안 쓰고 싶으면 — 스킬 한 줄

규칙서를 처음부터 쓰는 게 부담이면 이미 만들어진 구현체가 있다.

```bash
npx add-skill Astro-Han/karpathy-llm-wiki
```

Agent Skills 표준을 따르므로 **클로드 코드·커서·오픈코드**에서 그대로 쓸 수 있다. 코덱스 CLI는 스킬 디렉터리에 복사하면 된다. MIT 라이선스다. 설치하면 ingest·query·lint 세 작업을 바로 시킬 수 있다.

## RAG와 언제 갈리나

답부터: **소스 수로 갈린다.**

| | RAG | **LLM Wiki** |
|---|---|---|
| 상태 | 무상태 — 질의마다 독립 | **유상태 — 지식이 쌓임** |
| 인프라 | 벡터DB, 임베딩 파이프라인 | **마크다운 폴더** |
| 교차 참조 | 질의할 때마다 발견 | **미리 만들어 둠** |
| 유지보수 | 임베딩 갱신 필요 | 넣을 때마다 AI가 갱신 |
| 질의 비용 | 높음 (검색+재순위+생성) | 낮음 (목차 읽기) |
| 추적성 | 청크 단위 — 불완전 | **원본 파일까지** |

*비교 항목은 Starmorph 가이드 기준. 다만 질의 비용은 단정하기 어렵다 — 위키는 페이지 전문을 통째로 읽히므로, 위키가 커지면 청크만 가져오는 RAG보다 토큰이 더 들 수도 있다.*

**LLM Wiki가 유리한 경우**
- 소스가 **100개 안팎** — 카파시는 "소스 약 100개, 페이지 수백 개 규모까지 놀랄 만큼 잘 된다"고 썼다. 2차 가이드들은 50~200개를 범위로 본다
- 지식이 **쌓이는 것**이 중요
- 인프라를 최소로 하고 싶을 때
- 나중에 **왜 그렇게 답했는지 추적**해야 할 때

**RAG가 유리한 경우**
- 문서가 수백만 건
- 문서가 자주 바뀜
- **밀리초 단위 응답**이 필요
- 대규모 팀이 공유

**개인이나 소규모 팀이라면 거의 언제나 위키 쪽이다.** 벡터DB를 세우고 유지하는 비용이 얻는 것보다 크다.

## 옵시디언을 쓰고 있다면

답부터: **이미 절반쯤 만들어져 있다.**

옵시디언 보관함은 그대로 **마크다운 파일 폴더**다. `[[위키링크]]`도 같은 문법을 쓴다. **구조만 나누면 된다.**

- 기존 노트들 → `raw/`로
- AI가 만들 정리본 → `wiki/`로
- 규칙 → `CLAUDE.md`로

그리고 보관함 폴더에서 클로드 코드를 실행하면 된다. 별도 도구를 깔 필요가 없다.

**주의할 점이 하나 있다. 기존 노트를 `raw/`로 옮겼다면 그 뒤로는 그 파일들을 손으로 고치지 않는 게 원칙이다.** 고치고 싶은 내용이 생기면 새 자료로 넣는다. 원본이 흔들리면 추적이 끊긴다.

## 시작할 때 주의할 것

**첫째, 규칙서에 시간을 쓴다.** 폴더는 1분이면 만들지만 `CLAUDE.md`가 위키의 품질을 결정한다. 특히 **페이지에 `sources`와 `confidence`를 반드시 붙이게** 하는 규칙은 빼먹지 말자. AI가 쓴 글을 나중에 검증할 유일한 수단이다.

**둘째, 깃을 먼저 켠다.** ingest 한 번에 문서 열다섯 개가 바뀐다. 되돌릴 수 없으면 실수 한 번에 위키가 망가진다.

**셋째, 작게 시작한다.** 자료 다섯 개로 한 번 돌려 보고 위키가 어떻게 생기는지 확인한 뒤 규칙을 고치는 편이 낫다. 백 개를 한꺼번에 넣으면 구조가 마음에 안 들 때 되돌리기 힘들다.

**넷째, lint를 정기적으로 돌린다.** 위키는 반드시 망가진다. 월 1회 정도 점검을 돌려 모순과 고아 페이지를 정리하는 것을 루틴으로 잡자.

## 정리

**이 패턴의 핵심은 하나다. 답을 만드는 시점을 앞당기는 것이다.**

RAG는 질문받고 나서 답을 만든다. LLM Wiki는 자료를 받을 때 이미 만들어 둔다. 그래서 질문에 빠르고, 출처가 남고, **무엇보다 쓸수록 좋아진다.**

필요한 것은 폴더 세 개와 규칙 파일 하나다. 오늘 만들 수 있다.

```bash
mkdir -p ~/mywiki/{raw,wiki,outputs} && cd ~/mywiki && git init
```

여기서 시작해서, `CLAUDE.md`에 규칙을 적고, 자료를 넣고, AI에게 정리를 시키면 된다.

*이 글은 공개된 자료를 바탕으로 한 사용 안내이며 특정 도구 사용을 권유하지 않는다. LLM Wiki는 제품이 아니라 패턴이므로 구현체마다 세부가 다를 수 있고, 각 저장소의 최신 문서를 확인하기 바란다.*
