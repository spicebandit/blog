클로드 앱의 **Code 탭**을 열어는 봤는데 빈 입력창 앞에서 멈춘 분들을 위한 글입니다. 결론부터 말하면, 처음 시킬 일은 코딩이 아니라 **"파일을 만지는 반복 작업"**입니다. 엑셀 여러 개 합치기, 다운로드 폴더 정리, PDF에서 항목만 뽑기 — 이런 건 코드를 한 줄도 안 읽어도 결과를 눈으로 검증할 수 있어서 처음 쓰기에 가장 안전합니다.

아래 다섯 개는 **제가 실제로 돌려보고 결과와 실패를 확인한 것**만 올렸습니다. 지시문은 그대로 복사해 붙이면 되고, 각 예시 끝에 "제가 실제로 막혔던 지점"을 붙였습니다. 한글 파일을 다루는 순간 터지는 함정이 두 개 있는데(인코딩·PDF 한글 추출), 둘 다 아래에서 실측 결과로 보여드립니다.

| 예시 | 한 줄 지시 | 가장 흔한 실패 |
|---|---|---|
| **① CSV·엑셀 병합** | "이 폴더 월별 파일을 하나로 합치고 월×지역 집계표까지" | **엑셀이 저장한 한글 CSV 인코딩** — 날짜 칸이 통째로 비거나 읽다가 멈춥니다 |
| **② 폴더 정리** | "다운로드 폴더를 연·월/확장자별로 분류. **먼저 계획만 출력**" | 계획 확인 없이 바로 이동시켜 **되돌릴 수 없게** 됩니다 |
| **③ PDF 항목 추출** | "PDF 12개에서 업체명·날짜·합계금액만 뽑아 표로" | **한글만 깨져 나오는 PDF** — 숫자는 멀쩡해서 더 위험합니다 |
| **④ 공개 데이터 수집** | "이 공개 API에서 환율 받아 날짜별로 CSV에 쌓는 스크립트" | 리다이렉트·robots·이용약관 확인 누락 |
| **⑤ 한 장 웹페이지** | "이 CSV를 읽어 표와 막대그래프를 보여주는 HTML 한 장" | 결과를 브라우저로 안 열어보고 끝냅니다 |

## 시작 전 — 셋업은 이 글이 아니라 저 글에서

답부터: **앱 설치·Code 탭·폴더 고르기·권한 모드는 지난 글에서 다 다뤘습니다.** 처음이라면 [클로드 코드 사용방법 — 클로드 앱에서 터미널 없이 시작하기](/blog/2026-10-15-claude-app-claude-code-how-to-use/)를 먼저 보시고 오세요. 이 글은 그 다음 질문, **"열었는데 뭘 시키나"**만 다룹니다.

세 줄로 요약하면 이렇습니다. ①클로드 데스크톱 앱을 깔면 **클로드 코드가 이미 들어 있습니다**(Node.js·CLI 설치 불필요). ②상단 **Code 탭** → 환경 선택에서 **Local** → 작업할 폴더 지정. ③보내기 버튼 아래 줄에서 **권한 모드**를 고릅니다. 유료 구독(Pro·Max·Ultra·Team·Enterprise 중 하나)이 필요합니다.

아래 예시는 전부 **파일을 실제로 만들고 고치는** 작업입니다. 그래서 권한 모드를 먼저 정해두셔야 합니다. 공식 문서 기준으로 모드별 동작은 이렇습니다.

| 모드 | 파일 편집 | 터미널 명령 | 이 글의 예시에 쓸 때 |
|---|---|---|---|
| **Plan** | **안 함** (읽기·탐색만 하고 계획을 제안) | 탐색용. 단 자동 모드가 가능한 세션에선 분류기가 대신 판단(물어보지 않음) | 큰 작업 전에 접근 방법을 먼저 받을 때 |
| **Manual** | 매번 물어봄 | 매번 물어봄 | **처음이면 이것.** 공식 문서상 자동 허용은 '읽기만' |
| **Accept edits** | 자동 수락 (+ 파일 명령 `mkdir`·`touch`·`rm`·`rmdir`·`mv`·`cp`·`sed`) | 그 외 명령은 물어봄 | 같은 작업을 두 번째 돌릴 때 |
| **Auto** | 자동 | 셸·네트워크 실행 전 분류기가 요청과 맞는지 검사 | 익숙해진 뒤 |

여기서 한 가지만 기억하시면 됩니다. **Accept edits가 자동 수락하는 파일 명령에는 `mv`(이동)만 있는 게 아니라 `rm`(삭제)과 `sed`(내용 일괄치환)도 들어 있습니다.** 적용 범위는 작업 폴더(와 추가로 허용한 폴더) 안의 경로입니다. 예시 ②번 폴더 정리를 Accept edits로 돌리면 파일이 묻지 않고 움직입니다. 그래서 ②번은 **Manual로 시작**해야 합니다. 다만 `rm -rf /`나 `rm -rf ~`처럼 치명적 경로를 지우는 명령은 **어떤 모드에서도 자동 수락되지 않습니다** — 허용 규칙이나 훅으로도 통과시킬 수 없다고 공식 문서가 못 박아 뒀습니다.

(문서에는 이 넷 말고 **Bypass permissions**와 **Don't ask**도 있습니다. 앞의 것은 격리된 컨테이너·VM 전용이니 이 글 범위에서는 쓰지 마세요.)

## 지시문 쓰는 법 — 공식 문서가 말하는 건 세 가지뿐

답부터: **①구체적으로 쓰고 ②맞았는지 확인할 수단을 주고 ③증거를 요구한다.** 클로드 코드 공식 베스트 프랙티스 문서가 권하는 핵심이 이 셋입니다.

**①구체적으로.** 공식 문서의 대조 예시는 이렇습니다.

| 이렇게 쓰지 말고 | 이렇게 |
|---|---|
| "로그인 버그 고쳐줘" | "세션 만료 후 로그인이 실패한다는 제보가 있다. `src/auth/`의 토큰 갱신을 보고, **재현하는 실패 테스트를 먼저 쓰고**, 그다음 고쳐라" |
| "캘린더 위젯 추가해줘" | "`HotDogWidget.php` 패턴을 따라 월 선택과 연도 이동이 되는 캘린더 위젯을 만들어라. **새 라이브러리는 쓰지 마라**" |

사무 업무로 옮기면 이렇게 됩니다. "엑셀 정리해줘"가 아니라 **"`sales/` 폴더의 월별 CSV를 하나로 합치고, 열은 날짜·지역·품목·수량·금액 순서로, 금액은 숫자로, 결과는 `merged.csv`로 저장해라"**입니다.

**②확인 수단을 준다.** 문서의 표현은 "클로드에게 **통과/실패로 돌아오는 것**을 하나 줘라. 그러면 스스로 루프를 닫는다"입니다. 개발자에게는 테스트 코드지만, 사무 작업에서는 **대조 가능한 숫자 한 개**면 됩니다. "원본 3개 파일의 금액 합계와 병합 파일의 합계가 같은지 확인하고, 다르면 원인을 찾아 고쳐라" — 이 한 줄이 테스트 코드와 같은 역할을 합니다.

**③증거를 요구한다.** 문서는 이렇게 못 박습니다. *"'테스트가 다 통과했다'는 말 자체로는 알 수 있는 게 거의 없다."* 그래서 **실행한 명령과 그 출력**을 요구하라고 합니다. 사무 작업이면 "병합 전 행 수, 병합 후 행 수, 양쪽 합계를 출력해라"가 그 요구입니다.

한 가지 덧. 공식 문서는 `think step by step`이나 `be thorough` 같은 문구는 **특별한 키워드가 아니라 평범한 프롬프트 문장**이라고 밝힙니다. 약간의 유도 효과는 남지만, "얼마나 깊이 생각할지"를 정하는 건 별도의 **effort(노력) 설정**이라는 설명입니다. 다만 **`be ambitious`(욕심내서 해라)**는 여전히 효과가 있다고 적어뒀습니다. 클로드는 요청을 보수적으로 읽어 "최소한으로 만족시키는 것"을 만드는 경향이 있어서, 더 꽉 찬 결과를 원하면 그걸 말해줘야 한다는 설명입니다.

> **이 글의 지시문은 어디서 돌렸나** — 아래 예시는 macOS에서 샘플 파일을 만들어 클로드 코드로 실제 실행한 것입니다. 앱의 Code 탭과 터미널 CLI는 **같은 엔진**이라 동작과 결과가 같습니다(공식 문서: "Claude Code runs the same underlying engine everywhere"). 다른 점은 검토 화면·레이아웃 같은 껍데기입니다. 샘플은 3개월치 매출 CSV 8행짜리 소규모 데이터이고, 실제 업무 파일은 열 이름·행 수가 다를 테니 지시문의 파일명·열 이름만 바꿔 쓰시면 됩니다.

## 예시 ① — 월별 CSV·엑셀 파일을 하나로 합치고 집계까지

**①어떤 상황인가.** 월별로 쪼개진 매출 파일이 폴더에 쌓여 있고, 분기 보고 때마다 복사·붙여넣기로 합치는 상황입니다. 사무직이 가장 많이 겪는 일이고, 손으로 하면 행이 빠져도 모릅니다.

**②붙여넣을 지시문.**

```text
sales/ 폴더에 월별 매출 CSV가 여러 개 있다. 다음을 해라.

1. 전부 하나로 합쳐 merged.csv로 저장한다. 열은 date, region, product, qty, amount 순서.
2. 파일마다 인코딩이 다를 수 있다(엑셀이 저장한 한글 CSV 포함). 깨지지 않게 처리해라.
3. 월 × 지역 금액 집계표를 만들어 화면에 출력한다.
4. 검증: 원본 파일들의 amount 합계와 merged.csv의 합계가 같은지 확인하고,
   원본 행 수 / 병합 행 수 / 양쪽 합계를 출력해라. 다르면 원인을 찾아 고쳐라.
```

**③클로드가 무엇을 하는가.** 폴더를 읽어 파일 목록과 각 파일의 첫 줄(헤더)을 확인하고, 작은 스크립트를 하나 만들어 돌립니다. 핵심은 4번입니다 — 합계가 안 맞으면 클로드가 **스스로** 원인(인코딩·헤더 불일치)을 찾아 다시 돌립니다. 제 샘플에서 나온 출력은 이랬습니다.

```text
rows: 8  amount sum: 3,400,000

월       | 광주      | 대구      | 부산      | 서울        | 합계
2026-09  | 0        | 0        | 120,000  | 1,050,000  | 1,170,000
2026-10  | 0        | 300,000  | 150,000  | 880,000    | 1,330,000
2026-11  | 660,000  | 0        | 0        | 240,000    | 900,000
```

**④검토·수락에서 볼 것.** diff 화면에서 **새로 생긴 파일(`merged.csv`)과 스크립트 파일**을 확인합니다. 셋만 보시면 됩니다. ⓐ**행 수**가 원본 합과 같은가 ⓑ**합계**가 같은가 ⓒ**날짜 칸이 빈 행이 없는가**. 셋 중 하나라도 어긋나면 수락하지 말고 그대로 지적하세요. diff에서 해당 줄 번호 옆 **+** 버튼을 눌러 코멘트 상자를 열고, 내용을 적고 `Enter`로 추가합니다. 여러 줄에 다 달았으면 macOS는 `Cmd+Enter`, 윈도우는 `Ctrl+Enter`로 한꺼번에 제출하면 클로드가 읽고 고칩니다.

**⑤흔한 실패 — 한글 CSV 인코딩, 이게 1번 함정입니다.** 제가 실제로 재현한 두 가지입니다.

첫째, **엑셀이 저장한 UTF-8 CSV에는 BOM이라는 눈에 안 보이는 표식**이 맨 앞에 붙습니다. 그러면 첫 열 이름이 `date`가 아니라 `﻿date`로 읽힙니다. 증상이 고약합니다 — **에러가 안 납니다.** 그 파일에서 온 행들만 날짜 칸이 조용히 비고, 합계는 맞으니 검증도 통과합니다. 제 실측에서 세 번째 파일의 헤더가 이렇게 읽혔습니다.

```text
sales/2026-09.csv ['date', 'region', 'product', 'qty', 'amount']
sales/2026-10.csv ['date', 'region', 'product', 'qty', 'amount']
sales/2026-11.csv ['﻿date', 'region', 'product', 'qty', 'amount']   ← 첫 열 이름이 다르다
```

둘째, **윈도우 엑셀에서 "CSV(쉼표로 분리)"로 저장하면 UTF-8이 아니라 cp949(EUC-KR을 확장한 윈도우 전용 코드)**로 저장되는 경우가 많습니다. 이쪽은 반대로 요란하게 터집니다.

```text
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xbc in position 43: invalid start byte
```

**왜 아직도 이런 일이 생기나.** 두 증상은 버그가 아니라 세 세대의 표준이 한 폴더에 섞여 있는 것입니다. 1987년 한국 표준(KS C 5601:1987)은 한글 11,172자 가운데 **자주 쓰는 2,350자만** 코드로 정해뒀습니다 — 그래서 "똠", "뜽" 같은 글자를 쓸 수 없었고, 조합형이냐 완성형이냐를 두고 벌어진 논쟁은 1990년 국립국어원 학술지에 찬반 양론이 나란히 실릴 정도로 뜨거웠습니다. 마이크로소프트는 윈도우 95 한국어판부터 여기에 **8,822자를 덧붙여** 11,172자를 다 담은 cp949를 썼고, 그것이 지금도 윈도우 엑셀의 기본 저장 코드로 남아 있습니다. BOM은 그 반대쪽 유산입니다 — CSV에는 자기 인코딩을 적어두는 칸이 없어서, 엑셀이 UTF-8로 저장할 때 "이건 UTF-8이다"라는 세 바이트 표식을 맨 앞에 붙입니다. 유니코드 표준 자체는 UTF-8에 BOM을 **"요구하지도 권하지도 않는다"**고 못 박았는데도 그렇습니다. 사무실 CSV를 열 때마다 1987년과 1995년과 현재가 한꺼번에 맞닥뜨려지는 셈입니다.

**대처는 지시문 한 줄입니다.** 위 지시문 2번("파일마다 인코딩이 다를 수 있다. 깨지지 않게 처리해라")을 넣어두면 클로드가 BOM 처리와 cp949 자동 감지를 넣습니다. 안 넣었다면 이렇게 지적하세요 — **"11월 파일에서 온 행의 날짜가 비어 있다. 인코딩과 헤더를 다시 확인해라."** 그리고 애초에 **원본을 복사해 둔 폴더에서 작업하라고 지시**하는 게 제일 안전합니다.

## 예시 ② — 다운로드 폴더를 연·월/확장자별로 정리

**①어떤 상황인가.** 다운로드 폴더에 수백 개가 섞여 있고, 지난달 받은 계약서를 못 찾는 상황입니다. **이 예시만 성격이 다릅니다 — 파일을 움직이는 작업이라 되돌리기가 어렵습니다.** 그래서 지시문에 안전장치를 박아 넣습니다.

**②붙여넣을 지시문.**

```text
~/Downloads 를 정리하고 싶다. 수정일 기준 연-월 폴더 아래 확장자별 폴더로 분류해라.
단, 다음 순서를 지켜라.

1. 먼저 "원본 → 이동 위치" 계획만 표로 출력하고 멈춰라. 파일은 건드리지 마라.
2. 같은 이름이 이미 있는 경우(덮어쓰기 위험)는 표에 따로 표시해라.
3. 내가 "진행"이라고 답한 뒤에만 실제로 이동해라.
4. 이동한 뒤에는 되돌릴 수 있는 기록(어디서 어디로 옮겼는지 목록)을 파일로 남겨라.
```

**③클로드가 무엇을 하는가.** 1번 때문에 첫 턴에서는 **아무 파일도 움직이지 않고** 계획만 뱉습니다. 제 샘플 폴더에서 나온 출력입니다.

```text
원본                           -> 이동 위치
dl/IMG_4821.jpg              -> dl/2026-10/jpg/IMG_4821.jpg
dl/IMG_4822.jpg              -> dl/2026-11/jpg/IMG_4822.jpg
dl/계약서_최종.pdf             -> dl/2026-09/pdf/계약서_최종.pdf
dl/보고서.xlsx                -> dl/2026-11/xlsx/보고서.xlsx
dl/설치파일.dmg                -> dl/2026-11/dmg/설치파일.dmg

총 5개. 실제 이동은 하지 않았습니다(계획만 출력).
```

**④검토·수락에서 볼 것.** 이 예시에서 봐야 할 건 diff가 아니라 **위 표 자체**입니다. ⓐ**엉뚱한 폴더로 가는 파일이 없는가**(앱 설치파일이 서류 폴더로 들어가지 않는지) ⓑ**덮어쓰기 표시가 붙은 줄이 있는가** ⓒ**개수가 내 예상과 맞는가**. 그리고 **권한 모드를 다시 확인하세요.** Accept edits는 `mv`를 자동 수락하므로, 클로드가 1번 지시를 건너뛰는 순간 파일이 이미 움직여 있습니다. **이 예시는 Manual에서 시작하세요.** Manual은 공식 문서상 자동 허용이 '읽기만'이라 이동이 확실히 막힙니다. Plan은 계획을 먼저 받기에는 좋지만, 자동 모드를 쓸 수 있는 세션에서는 셸 명령을 물어보지 않고 분류기 판단에 넘기는 설정(`useAutoModeDuringPlan`)이 기본값이라 `mv` 같은 Bash 명령까지 보장해 주지는 않습니다.

공식 문서에 이 구분이 정확히 설명돼 있습니다. 프롬프트에 쓴 "계획만 출력하고 멈춰라"는 **비결정적(non-deterministic) 지시** — 클로드가 읽고 판단하는 것이고, 대체로 따르지만 보장은 없습니다. 반면 **거부 규칙·훅·관리 설정**은 **결정적(deterministic)** — 클로드 코드(하네스)가 모델의 판단과 무관하게 매번 적용합니다. 권한 모드도 하네스가 거는 문턱이라 같은 쪽입니다. **되돌릴 수 없는 작업은 지시문이 아니라 모드로 막아야 한다**는 뜻입니다.

이 구분은 AI가 만든 문제가 아닙니다. 되돌릴 수 없는 작업 앞에 "하기 전에 보여주기"를 두는 관행은 소프트웨어가 반세기 동안 쌓아온 것입니다. 되돌리기(undo)는 1968년 브라운대학교의 FRESS가 처음 넣은 기능으로 알려져 있고, 1976년 벨연구소에서 만든 유닉스 빌드 도구 `make`는 1979년 V7 매뉴얼에서 이미 `-n` 옵션을 "실행할 명령을 **출력하되 실행하지 않는다**"로 설명해뒀습니다. 지금 `rsync --dry-run`이나 `terraform plan`이 하는 일이 그것이고, 예시 ②의 1번 지시가 하는 일도 같습니다. 다만 결정적인 차이가 하나 있습니다 — `make -n`은 **프로그램의 기능**이라 어기는 일이 없고, "계획만 출력해라"는 **읽고 판단하는 쪽에 맡긴 부탁**입니다. 반세기 된 관행이 안전했던 이유는 그것이 부탁이 아니었기 때문입니다. 그래서 모드로 막아야 합니다.

*Photo by [cottonbro studio](https://www.pexels.com/@cottonbro) on [Pexels](https://www.pexels.com/photo/cardboard-box-full-of-file-folders-8371705/)*

**⑤흔한 실패.** 세 가지입니다. ⓐ**수정일과 받은 날짜가 다릅니다** — 파일을 복사·편집하면 수정일이 갱신되므로 "작년에 받은 파일"이 올해 폴더로 갈 수 있습니다. 날짜 기준이 중요하면 지시문에 "수정일 기준"이라고 명시하거나 생성일로 바꿔달라고 하세요. ⓑ**확장자 없는 파일·숨김 파일** 처리를 안 정해주면 제멋대로 갑니다. ⓒ**클라우드 동기화 폴더(아이클라우드·드라이브·드롭박스)에서 돌리면 동기화와 충돌**합니다. 다운로드 폴더처럼 동기화 대상이 아닌 곳에서 먼저 연습하세요.

## 예시 ③ — PDF 여러 개에서 항목만 뽑아 표로 (한글 함정 주의)

**①어떤 상황인가.** 견적서·세금계산서 PDF가 수십 개 있고, 거기서 업체명·날짜·합계금액만 뽑아 엑셀로 만들어야 하는 상황입니다. 손으로 하면 한 건에 30초, 50건이면 25분입니다.

**②붙여넣을 지시문.**

```text
quotes/ 폴더의 PDF에서 업체명, 견적일, 합계금액만 뽑아 quotes.csv로 만들어라.

1. 먼저 PDF 1개로만 시험해서 추출된 원문 텍스트를 그대로 보여줘라.
   한글이 깨져 나오는지 내가 눈으로 확인하겠다.
2. 한글이 깨지면 텍스트 추출을 포기하고 OCR 경로로 바꿔라(이유도 설명해라).
3. 전체를 돌린 뒤, 금액 칸이 비었거나 0인 행을 따로 목록으로 알려줘라.
4. 추출 실패한 파일은 지우지 말고 실패 목록에 남겨라.
```

**③클로드가 무엇을 하는가.** 1번이 이 지시문의 전부입니다. PDF는 겉보기가 같아도 속이 세 종류라서, **한 개로 시험해 보지 않으면 50개를 잘못 뽑습니다.**

**이 예시는 '흔한 실패'를 먼저 봐야 합니다 — 제가 실제로 당한 것.** 한글 견적서 PDF에서 텍스트를 바로 뽑았더니 이렇게 나왔습니다.

```text
추출 텍스트: 'Ѽ੸ࢲ  \nস୓ݺ :оա׮੹ӝ  \nѼ੸ੌ: 2026-11-10  ...'
```

원문은 `견적서 / 업체명: 가나다전기 / 견적일: 2026-11-10`입니다. **한글만 깨지고 숫자와 영문은 멀쩡합니다.** 이게 왜 위험한지 아시겠지요 — 금액과 날짜는 정상으로 보여서, 업체명 칸만 이상한 걸 보고 "폰트 문제인가" 하고 넘어가기 쉽습니다. 스캔 문서가 아니라 **텍스트층이 분명히 있는 PDF**인데도 이렇게 됩니다. PDF 내부에서 글자가 폰트별 코드로 저장돼 있고 그 대응표(ToUnicode)가 빠져 있으면 생기는 일입니다.

설계 자체가 그렇습니다. PDF는 1991년 어도비 공동창업자 존 워녹의 사내 기획("카멜롯")에서 출발했고, 목표는 **어디서 열어도 인쇄된 모양이 똑같이 재현되는 것**이었습니다. 글자 코드를 유니코드로 되돌리는 대응표(ToUnicode)는 1996년 PDF 1.2에서 뒤늦게 추가된, 그마저도 **선택 항목**입니다. 모양을 지키는 건 보장이고 글자를 되읽는 건 호의인 형식이라, 겉보기가 멀쩡한데 추출만 깨지는 일은 PDF의 사고가 아니라 설계의 결과입니다.

OCR로 경로를 바꾸면 복원됩니다. 같은 파일을 이미지로 바꾼 뒤 OCR을 돌린 실제 결과입니다.

```text
견적서

염체명: 가나다전기      ← '업체명'을 '염체명'으로 오인

견적일: 2026-11-10
합계금액: 4,730,000원   ← 금액은 정확
```

**복원은 되지만 오타가 섞입니다.** 4줄 중 1곳이 틀렸습니다. 다행히 이번엔 금액이 맞았지만, 반대로 금액의 숫자 한 자리가 틀릴 수도 있습니다. 그래서 OCR 경로로 갔다면 **금액은 반드시 원본과 대조**해야 합니다.

## 예시 ④ — 공개 데이터를 받아 날짜별로 쌓기

**①어떤 상황인가.** 환율·금리·유가처럼 매일 바뀌는 공개 지표를 보고서에 쓰는데, 매번 사이트에 들어가 손으로 적는 상황입니다.

**②붙여넣을 지시문.**

```text
아래 공개 API에서 원·달러 환율을 받아 date,krw 두 열로 rates.csv에 한 줄씩 쌓는
스크립트를 만들어라. https://api.frankfurter.dev/v1/latest?base=USD&symbols=KRW

1. 먼저 그 URL을 한 번 호출해 받은 원문(JSON)을 그대로 보여줘라.
2. 같은 날짜가 이미 있으면 중복 추가하지 말고 건너뛰어라.
3. 호출이 실패하면 기존 CSV를 건드리지 말고 사유를 출력해라.
4. 그 사이트의 이용약관·robots.txt에 자동 호출 제한이 있는지 확인해 알려줘라.
```

**③클로드가 무엇을 하는가.** 1번에서 실제 응답을 보여줍니다. 제가 호출한 결과입니다.

```json
{"amount":1.0,"base":"USD","date":"2026-11-17","rates":{"KRW":1336.21}}
```

4번에서는 `robots.txt`를 확인해 알려줍니다(이 API는 `User-agent: * / Allow: /`였습니다). **4번을 꼭 넣으세요.** 공개 데이터라도 사이트마다 자동 수집 조건이 다르고, 로그인이 필요한 페이지나 약관이 금지한 곳을 긁는 건 다른 문제가 됩니다. 애초에 **API가 있으면 API를 쓰는 게 맞습니다** — 화면을 긁는 방식은 사이트 디자인이 바뀌면 조용히 망가집니다.

**④검토·수락에서 볼 것.** ⓐ응답 원문의 **날짜를 확인하세요**. **오늘 날짜가 아닌 게 정상일 수 있습니다** — 이 API가 쓰는 유럽중앙은행 참조환율은 유럽 영업일 오후에 발표되므로, 한국 시간 아침에 호출하면 직전 영업일 값이 옵니다. 위 호출도 수요일인 11월 18일 아침에 돌렸는데 `date`가 화요일인 11월 17일이었습니다(주말·공휴일에도 마찬가지입니다). 날짜 기준이 중요한 보고서라면 이 지연을 전제로 써야 합니다. ⓑ**실패 시 기존 파일을 건드리지 않는지**(지시문 3번) ⓒ**키가 코드에 박혀 있지 않은지.** API 키가 필요한 서비스라면 키를 코드에 쓰지 말고 환경변수로 빼달라고 하세요. 그 파일을 나중에 누군가에게 보내면 키가 같이 갑니다. ⓓ**응답 헤더도 보라고 시키세요.** 확인 시점에 위 v1 주소는 `Deprecation` 헤더(2026-05-18)와 후속 버전(`/v2/rates`) 안내를 함께 내려줬습니다. 지금은 정상 동작하지만, 매일 돌릴 스크립트라면 지시문에 **"응답 헤더에 Deprecation·Sunset이 있는지 확인해 알려줘라"** 한 줄을 더 넣는 게 좋습니다.

**⑤흔한 실패.** ⓐ**리다이렉트.** 제가 처음 호출한 주소는 301로 넘어가며 HTML만 돌려줬습니다(`301 Moved Permanently`). 클로드에게 "JSON이 아니라 HTML이 왔다"고 알려주면 리다이렉트를 따라가게 고칩니다. ⓑ**호출 간격.** 매분 호출할 이유가 없는 데이터를 매분 받으면 차단됩니다. 하루 1회로 충분한 데이터면 그렇게 지시하세요. ⓒ**자동 실행은 별도 설정이 필요합니다.** 앱의 **예약 작업(Scheduled tasks)**을 쓰면 매일 아침 같은 주기로 돌릴 수 있지만, 설정이 따로 있습니다. 로컬 세션 자체는 앱을 닫으면 멈춥니다.

## 예시 ⑤ — 결과가 눈에 보이는 것으로 마무리: 한 장짜리 웹페이지

**①어떤 상황인가.** 앞의 예시들은 결과가 CSV라 "잘 된 건가" 감이 안 옵니다. 마지막은 **화면에 보이는 결과물**로 끝내는 게 좋습니다.

**②붙여넣을 지시문.**

```text
merged.csv를 읽어서 월별 합계 표와 막대그래프를 보여주는 HTML 한 장을 만들어라.

1. 파일 하나로 끝내라(외부 라이브러리·CDN 없이). 더블클릭해서 열리게.
2. 숫자는 천 단위 쉼표, 금액 단위를 표에 적어라.
3. 만든 뒤 브라우저에서 직접 열어 보고, 표의 합계가 CSV 합계와 같은지 확인해 보고해라.
4. be ambitious: 데이터가 없을 때 보여줄 화면과 인쇄했을 때의 모양도 챙겨라.
```

**③클로드가 무엇을 하는가.** HTML 파일 하나를 만들고, 앱에서는 **Browser 창(Cmd+Shift+B)**에 띄워 직접 보면서 고칩니다. 공식 문서가 말하는 **앱 미리보기**가 이 대목에서 가장 체감됩니다 — 클로드가 자기가 만든 화면을 보고 수정하는 흐름은 터미널에서는 번거롭습니다.

**④검토·수락에서 볼 것.** ⓐ**브라우저에서 실제로 열어보기.** HTML은 코드가 멀쩡해도 화면이 깨질 수 있습니다. ⓑ**표의 합계와 CSV 합계 대조**(지시문 3번). ⓒ**외부 CDN을 썼는지** — 지시문 1번을 넣었는데도 차트 라이브러리를 불러왔다면 인터넷 없는 환경에서 그래프가 사라집니다.

**⑤흔한 실패.** ⓐ**숫자가 문자열로 정렬**됩니다("1,000,000"이 "900,000"보다 작게 정렬). 보고서에 쓰기 전에 정렬을 한 번 확인하세요. ⓑ**한글 폰트.** 폰트를 지정하지 않으면 환경에 따라 모양이 달라집니다. ⓒ**4번의 `be ambitious`를 빼면** 표와 그래프만 있는 최소 결과물이 나옵니다. 공식 문서가 설명한 그대로입니다 — 클로드는 요청을 보수적으로 읽습니다.

## 앱에서 안 되는 것 — 터미널 CLI와의 선

답부터: **앱으로 거의 다 되지만, 스크립팅과 Agent SDK는 터미널 CLI 전용입니다.** 공식 문서의 표현은 "CLI는 터미널 작업에서 가장 완전한 표면이며, 스크립팅과 Agent SDK는 CLI에만 있다"입니다. 되는 것처럼 써두면 독자가 막히니 정확히 적어둡니다.

| 하려는 것 | 데스크톱 앱 | 참고 |
|---|---|---|
| 위 예시 ①~⑤ 전부 | **된다** | 로컬 세션 + Local 환경 |
| 변경 내용 diff로 검토·줄 코멘트 | **된다**(앱의 강점) | CLI보다 편하다 |
| 앱을 닫아도 계속 돌리기 | 로컬 세션은 **멈춘다** | **클라우드 세션**으로 보내면 계속된다 |
| 클라우드 세션에서 Manual 모드 | **안 된다** | Accept edits·Plan·Auto만 지원 |
| 클라우드·SSH·WSL에서 파일 직접 편집 | **보기 전용** | 클로드에게 고치라고 해야 한다 |
| 플러그인 설치 | 클라우드·WSL 세션에서 **안 된다** | 로컬은 된다 |
| 앱 미리보기(Browser 창) | SSH에선 **클로드가 직접 못 쓴다** | 내가 보려면 포트 포워딩. HTML 파일 하나는 채팅의 파일 경로를 클릭해 미리보기 가능 |
| 내 화면·앱을 클로드가 직접 조작(컴퓨터 사용) | Pro·Max·Ultra만. **기본은 꺼져 있다** | Team·Enterprise 미지원. macOS·윈도우 **리서치 프리뷰**(macOS는 14 이상) |
| 쉘 스크립트에서 클로드 호출, Agent SDK | **안 된다 — CLI 전용** | 자동화 파이프라인을 짤 때 |

설정·프로젝트 메모리(`CLAUDE.md`)·MCP 서버는 로컬 표면끼리 공유됩니다. 앱으로 시작했다가 나중에 CLI를 깔아도 **같은 프로젝트에서 설정이 그대로 따라옵니다.**

## So What — 고를 기준은 "코딩이냐"가 아니라 "되돌릴 수 있냐"다

이 글에서 추린 다섯 개를 다시 보면 공통점이 하나 있습니다. **전부 결과를 숫자나 화면으로 대조할 수 있는 작업**입니다. 합계가 맞는지, 파일 개수가 맞는지, 브라우저에서 열리는지. 공식 문서가 "통과/실패로 돌아오는 것을 하나 줘라"고 말한 것이 개발자용 조언처럼 보이지만, 실은 **비개발자에게 더 중요한 조언**입니다. 코드를 못 읽을수록, 결과를 대조할 숫자 하나가 유일한 안전장치가 되기 때문입니다.

그래서 처음 시킬 일을 고르는 기준은 "코딩이냐 아니냐"가 아닙니다. **되돌릴 수 있느냐**입니다. 순서로 쓰면 이렇습니다.

1. **새로 만드는 것부터.** 병합 파일 만들기(①), 표 만들기(⑤)처럼 원본을 건드리지 않는 작업은 틀려도 지우면 끝입니다.
2. **읽기만 하는 것 다음.** PDF에서 뽑기(③), 데이터 받아오기(④)는 원본을 수정하지 않습니다.
3. **원본을 움직이는 것은 맨 마지막.** 폴더 정리(②)는 모드로 막고, 계획을 먼저 받고, 복사본에서 연습한 뒤에 하세요.
4. **매번 검증 한 줄을 붙이세요.** "합계가 같은지 확인하고 실행한 명령과 출력을 보여줘라" — 이 한 줄이 들어간 지시문과 안 들어간 지시문의 결과 차이가, 모델을 바꾸는 것보다 큽니다.

빈 입력창 앞에서 멈췄다면, 지금 책상에서 **이번 주에 두 번 이상 손으로 한 파일 작업**을 하나 떠올려 보세요. 그게 첫 지시문입니다.
